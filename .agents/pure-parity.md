# Pure parity checklist

This file is the working checklist for requests that say papyrus should copy,
adapt, or prioritize behavior that already exists in Pure. It does not mean every
item is visually identical today. It records the source to inspect first, the
papyrus owner, the current state, and the next evidence needed before a row in
`.agents/request-audit.md` can be marked fully verified.

When implementing or polishing one of these areas, check Pure first. If the Pure
code fits the package boundary, adapt the component shape or behavior in
papyrus. If it does not fit, record the reason before building a local variant.

## Pure wrapper decisions

These decisions keep `papyrus` thin without making the package depend on
Pure private internals or forcing Pure's full site assumptions into every
consumer.

| Component / behavior | Decision | Reason |
| --- | --- | --- |
| Pure user components | Direct pass-through via `astro-papyrus/pure/user`. | Public Pure export; safe for consumers that want Pure primitives directly. |
| Pure advanced components | Direct pass-through via `astro-papyrus/pure/advanced`. | Public Pure export; exposes `GithubCard`, `LinkPreview`, `MediumZoom`, and related components without copying them. |
| Pure page components | Direct pass-through via `astro-papyrus/pure/pages`. | Public Pure export; consumers can opt into `PostPreview`, `TOC`, `BackToTop`, and page primitives directly. |
| `PapyrusGithubCard` | Keep local Papyrus implementation for now. | It is browser-verified with Papyrus tokens and does not require consumers to adopt Pure's UnoCSS classes. Pure's component remains available through `astro-papyrus/pure/advanced`. |
| `PapyrusLinkPreview` | Keep local static variant for now. | Pure's `LinkPreview` fetches OpenGraph through a private plugin import; the public Pure component is available for consumers, but Papyrus's local card avoids server fetch assumptions. |
| `PapyrusTimeline` | Keep local Papyrus implementation for now. | The props intentionally mirror Pure's simple event model while using Papyrus tokens and CV/profile layout needs. Pure's `Timeline` remains available through `astro-papyrus/pure/user`. |
| `PapyrusPostList` | Keep local adapter for package posts pages. | Pure `PostPreview` expects Pure collection shapes and `/blog/${id}` routing. Papyrus supports list, compact, and cards views, pinned posts, `/posts/`, and tag search links. Pure page components remain available through `astro-papyrus/pure/pages`. |
| `PapyrusToc` | Keep local collapsed TOC for posts. | Pure's TOC has progress/highlight behavior and private `toc` plugin usage; Papyrus currently needs a compact collapsible post TOC. Pure `TOC` remains available through `astro-papyrus/pure/pages`. |
| Back-to-top | Use `PapyrusBackToTopRuntime` in Papyrus layouts; expose Pure `BackToTop` via pass-through. | Pure's component expects specific header/content IDs and Pure utility classes. Papyrus's runtime preserves existing verified behavior and remains optional through `backToTop`. |
| Share/source actions, Mermaid/artifacts, image zoom | Use split Papyrus runtime components. | These are Papyrus-specific enhancements around source copy, share copy, theme-aware Mermaid rendering, artifact cards, and zoom overlay behavior. Code blocks use the Pure Shiki transformer behavior copied from upstream Pure. |

Checklist status rules:

- `Functional` means papyrus has a working local implementation and a focused verifier.
- `Pure-like` means the implementation was compared against a Pure source file or rendered Pure fixture.
- `Verified parity` requires repeatable browser evidence or a documented screenshot/PDF comparison.
- A broad build, link check, or script existence check is not enough to close a visual parity row.
