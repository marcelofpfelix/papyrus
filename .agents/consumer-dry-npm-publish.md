# Consumer DRY and npm publish task

## Goal

Keep `papyrus-template` easy to clone while making Papyrus the owner of shared
theme behavior. `marcelofelix` and `papyrus-template` should keep only local
content, local data, local config, deployment files, and site-specific public
assets.

This is the follow-up task for `PP-197`.

## Success criteria

- `papyrus-template` works as a GitHub template clone with a small local file
  set: config, sample content/data, public site identity assets, Makefile, CI,
  and README.
- `marcelofelix` consumes the same Papyrus package behavior and overrides only
  personal content/data/config/assets.
- Shared pages and routes are inherited from Papyrus unless the consumer has a
  real reason to override copy or composition.
- `astro-papyrus@0.2.2` is published to npm, but consumers can keep using the
  GitHub branch until the local 7-day package maturity policy allows installing
  the fresh npm release.
- After publishing, consumers can switch from:

```json
"astro-papyrus": "github:marcelofpfelix/papyrus#0.2.2"
```

to:

```sh
pnpm add astro-papyrus@^0.2.2
```

- The template README documents both paths clearly:
  - current GitHub dependency path for unreleased or too-fresh development;
  - npm dependency path after publish and the maturity gate;
  - cloning the template remains the recommended beginner flow.

## Package-boundary candidates

Move or expose these from Papyrus so consumers do not carry copies:

- Profile print routes: `src/pages/profile/print.astro` and
  `src/pages/profile/ast.astro`.
- Markdown defaults currently repeated in consumer `astro.config.mjs`, including
  callouts, Shiki/Pure behavior, custom languages, and hidden-post sitemap
  behavior where it is generic.
- `src/pages/llms.txt.ts` and related generated AI index route behavior.
- Timeline route aliases or redirects when the consumer only repeats package
  behavior.
- Content collection exports: consumers should prefer
  `export { collections } from "astro-papyrus/content"`.
- Site config glue that only exists because inherited pages are not complete.
- Profile/project data helpers that are currently hardcoded inside consumer
  source files instead of local TOML/data files or Papyrus conventions.
- CV print CSS if it is only needed by inherited print routes.

## Consumer assets

Keep local public assets only when they are site identity or content:

- favicons, logo, webmanifest, and app icons for the specific site;
- profile/CV downloads and generated exports for the specific profile;
- post cover images referenced by local post frontmatter;
- author photos and real content images.

Remove or stop copying demo assets into consuming repos:

- Papyrus demo cover images that are not referenced by consumer content.

## Current marcelofelix asset notes

- `public/icons/code.svg` was required only because Papyrus Shiki code-block UI
  referenced `/icons/code.svg#mingcute-*`. Papyrus now inlines those code-block
  icons in the Shiki transformer, so consumers should not need to carry that
  sprite file after they update to the fixed package ref.
- `public/images/new-web.svg` is generated by the local `cover:post` script, but
  `src/content/posts/new-web.md` currently does not declare it as `cover`. Either
  add `cover: /images/new-web.svg` if the post should use it, or remove the file
  and local script. The cover workflow should not silently create orphan assets:
  require an existing/frontmatter cover target, skip generation when no cover is
  configured, or provide an explicit command that also updates post metadata.
- `public/images/papyrus-dark.svg` and `public/images/papyrus-layout.svg` look
  like copied demo/template assets in `marcelofelix`; current source scans did
  not find local references. They should be removed from the consumer if a final
  asset audit confirms they are still unused.

## Implementation order

1. Make Papyrus export or inject the duplicated shared routes, defaults, and
   assets.
2. Reduce `papyrus-template` to the minimum clone-friendly starter surface.
3. Reduce `marcelofelix` to local config/content/data/assets only.
4. Run focused builds for Papyrus, `papyrus-template`, and `marcelofelix`.
5. Prepare npm metadata, files list, changelog, version, and release check.
6. Publish `astro-papyrus` when authorized. Done for `0.2.2` on 2026-08-13.
7. Switch consumers to npm after the package passes `minimumReleaseAge: 10080`
   and refresh lockfiles. Do not bypass this policy unless explicitly requested.

## Validation

- Papyrus: package export check, build, markdown/code verification, link check.
- `papyrus-template`: clean install, build, and smoke check inherited routes.
- `marcelofelix`: clean install, build, and smoke check local overrides.
- Skip Lighthouse during implementation; run it only before commit or release
  when explicitly requested.
